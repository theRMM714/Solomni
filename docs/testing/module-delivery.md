# 模块测试交付

> 本文是**模块作者要交付什么测试证据的唯一权威**；测试层级（T0-T5）、替身语义、隔离与清理、报告状态与缺口账格式
> 由 [TESTING.md](../../TESTING.md) 及其细则统一规定，本文不重复。
> 模块契约本体见 [MODULE_SPEC.md](../../MODULE_SPEC.md)。

## 一、最小可测性

模块交付时必须能说明并验证自己的行为边界。测试层级（T0-T5）、替身语义、隔离与清理、报告状态与缺口账格式
由 [TESTING.md](../../TESTING.md) 统一规定；本文只列**模块作者要交付什么**。

- 职责边界必须能在不依赖真实模型、真实供应商、真实密钥的条件下验证。
- 只提供 `system` 的模块，至少用一组可重复的输入场景检查职责边界、禁止事项与输出要求；这类检查不能伪装成工具进程测试。
- 声明 `tools` 的模块，工具必须能脱离核心独立运行：参数从 stdin 收 JSON、结果从 stdout 输出、失败经非零退出码或约定好的错误结果暴露。
- 测试只用模块契约允许的输入与路径模型，不写机器绝对路径、不依赖个人目录或真实凭据；测试之间相互隔离、不依赖执行顺序。

## 二、三类场景

每个能力先列适用场景，再按下表逐项给出结果或缺口：

```text
场景   | 输入/条件 | 预期结果 | 观察方式 | 当前状态
正常   | …         | …        | …        | pass / gap / env-skip
错误   | …         | …        | …        | pass / gap / env-skip
边界   | …         | …        | …        | pass / gap / env-skip / 不适用
```

- **正常**：最小有效输入、典型输入、一次完整成功流程；不用"没崩溃""返回非空"代替对行为的断言。
- **错误**：缺必填参数、格式错误、文件不存在、编码错误、依赖失败、超时、子进程非零退出、输出不可解析等；
  必须验证错误能被识别，且不会被静默改写成成功。
- **边界**：空输入、最小/最大长度、重复调用、中文与非 ASCII、换行差异、特殊字符、超大输出、并发或取消等。

`gap`、`env-skip` 与"不适用"都必须说明原因；不能用"以后补""本机没问题"这类不可判定的描述代替。

## 三、工具协议契约

对 `module.yaml` 里声明的每个工具，至少验证：

- stdin JSON 能被独立启动的工具正确解析；
- stdout 只输出约定的结果，不把调试信息混入协议；
- stderr、退出码与截断行为不会掩盖失败；
- 核心调用与独立启动使用同一套协议语义；
- 工具不存在、解释器不可用或运行能力缺失时，失败能如实暴露。

## 四、资源清理与跨平台假设

- 测试数据写入专用隔离根，不碰真实 `.home/`、真实 `session/`、模块 `userdata/` 或开发者本地配置；
  成功、失败、超时、中止与异常退出都要走清理路径，清理失败必须让测试失败或明确报告。
- 子进程、进程树、端口与文件句柄要有可观察的回收结果，不把"操作系统最终会回收"当作清理证据。
- 模块默认面向 Windows / macOS / Linux：路径用路径组件拼接、不假设某个 shell 或系统工具存在、
  stdin/stdout/stderr 使用明确编码、不依赖真实外网或真实密钥。
- 平台特有能力通过平台测试或平台探针验证；不具备条件时记 `env-skip` 或 `gap`，并写明原因与可执行的验证方法。
  确实只支持某个平台时，必须在职责或工具说明里写明限制，不能用跨平台措辞掩盖。

## 五、观察面

测试只根据公开且稳定的观察面判定结果：工具 stdout 的 JSON、stderr 与退出码、文件内容与目录布局、
记录型替身的调用记录、报告中的结构化字段。必须读私有状态、猜日志文案或依赖不可稳定解析的输出 = 观察面不足，
应先补稳定的输出契约或记录缺口；观察面只暴露判定行为所需的信息，不泄漏密钥与真实路径。

## 六、交付前检查清单

交付回报中至少说明：

- 正常、错误、边界场景分别在哪里测试；
- 用了哪些 Stub / Fake / Mock / Spy / Fixture，各自覆盖什么（语义见 [doubles.md](doubles.md)）；
- 工具协议或产品端口契约在哪里验证；
- 临时文件、进程、端口、日志等资源如何清理；
- Windows / macOS / Linux 的假设、已验证项与未验证项；
- 通过、缺口、环境跳过与"不适用"项的证据；
- 本次测试是否产生外部副作用，以及是否已清理。

回报中的"通过"只表示对应测试已实际执行并满足可判定验收条件；没有执行、环境不允许或尚无测试的能力，
必须分别写成 `gap`、`env-skip` 或其它适用状态，不得写成"已支持"。
