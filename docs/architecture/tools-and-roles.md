# 工具与角色

> 本文是**系统工具、角色（身份）、以及"谁能用哪些工具"的唯一权威**。
> 模块工具仍在各自 `module.yaml` 声明（见 [MODULE_SPEC.md](../../MODULE_SPEC.md)），本文只管系统工具。

**当前状态：已落地。** 两张表分别在 `systools/tools.yaml` 与 `systools/roles.yaml`；装配提示词、
发放工具面与越权校验都读它们（见 §三），代码里没有第二份"角色 → 工具"名单。

## 一、两个真相源，各一张表

| 表 | 回答什么 | 位置 |
| --- | --- | --- |
| **工具总表** | 工具**是什么**：id / desc / 参数 schema / 能否并发 / 能力 | `systools/tools.yaml` |
| **角色表** | 这个**身份有什么**：引用的系统工具 id + 提示词 | `systools/roles.yaml` |

代码里**不得**出现"哪个角色能调哪个工具"的判断：只有两个动作——**按角色组装工具面**、**按表校验调用**。

### 工具表字段

```yaml
tools:
  read:
    capability: fs-read        # 能力：决定收口（沙箱 / 围栏）
    desc: 读取文本文件（UTF-8）。
    parallel: true             # 同一回复里的多个调用能否真的并发跑
    params:                    # 既用于生成声明，也用于校验调用参数
      path:
        type: string
        required: true
        desc: 要读取的真实绝对路径
```

- **`capability` 决定收口，不按"系统/模块"一刀切**：`read`/`list`/`search`/`write`/`edit`/`patch` 虽然都是系统工具，但它们碰文件系统，**照样受沙箱与围栏约束**；`say`/`agree` 这类不碰文件。
- **列目录是"核实"的前提**：`read` 只读文件，`search` 要关键词，**没有 `list` 就确认不了"资料齐不齐、脚本在不在"**；`read` 遇到目录会如实引导到 `list`，不抛 IO 错。
- 参数不合法 → **如实拒绝并落工具行**，不静默。

### 角色表字段

```yaml
roles:
  discussant:
    prompt: roles/discussant          # 提示词与工具面**同处声明**
    tools: [say, agree, leave, ask, read, list, search]   # 讨论回合只做核实：读类 + 讨论动词
```

- **角色 = 场景绑定的身份**：`discussant` 只存在于讨论阶段，`orchestrator` 只存在于任务链推进阶段。**不再引入"阶段 → 工具"的第二张表**（否则两个真相源）。
- **角色表只引用系统工具**：模块工具是"这个 agent 的能力"，不是"这个角色的属性"，按成员归属自动获得。
- **不做角色继承**：重复列几个 id 没有代价，继承会引入隐式耦合。

## 二、可用工具面（运行时合成）

```
本会话可用工具 = 系统工具表 ∩ 该角色表  +  该成员所属模块的工具
```

越权防线因此分两段，缺一不可：系统工具查**角色表**；模块工具查**该成员有没有这个模块**（现状已有 module 消歧）。

**注入口径（唯一）**：**总表不进提示词**。每回合由核心查"这一回合的身份能用的工具"，把那一份的
说明与参数作为一条系统消息随回合注入；原生通道同时用它做工具声明槽。两个回合各一份：

| 回合 | 这一份是什么 |
| --- | --- |
| 讨论回合 | `discussant` 的面（发言动词 + 只读核实），**不含模块工具**（它不干活） |
| 执行回合 | `executor` 的面 + 该 agent 的模块工具（角色表的 `module_tools: true`） |

发放与校验因此是**同一份判据**：列出来的就是这一刻真能调的，没拿到的既不在提示词里、也不在声明槽里；
真去调它会被如实拒绝。

身份与环境同理：它们是**会话参数**（`session::SessionParams`），每次调用现渲染成系统消息，
不占对话的位置（见 [session-model.md](session-model.md) 四之二）。

核心自己的操作（`planner` / `orchestrator`）不走 agent 会话：原生通道由声明槽给出它们的面，
信封通道由各自的角色提示词写清载荷形状——总表同样不进提示词。

## 三、越权校验

**已落地（P5c）**：角色表不再只是渲染进提示词的清单——**工具面与越权校验都出自它**：
讨论回合按 `discussant` 发放并校验（面里没有的一律拒绝），单 agent 执行回合按 `executor` 校验。
代码里**没有任何**"哪个角色能调哪个工具"的名单，加一个工具只改 `systools/tools.yaml` 与 `roles.yaml`。


- **原生模式（供应商结构化槽位）与信封模式（正文里手写信封）走同一个校验点。** 两者在项目里是**互斥但等价**的；等价性一破，回放就与实时不一致。
- 越权调用 → **如实拒绝 + 落工具行**（用户要能看到"它越权了"，而不是"AI 没反应"）。
- **悬空引用**（角色引用了总表里不存在的工具 id）→ **结构审查硬失败**。这是两张表不漂的机制保证，不靠人看。

## 三之二、核心操作必须走工具调用

**规则**：任何**会驱动核心**的产出都必须是一次**工具调用**——建任务链、节点验收、总验收、
代拟或推荐名单、执行席回报。两条通道等价：原生走供应商的结构化槽位，信封走正文里的手写信封；
核心只从**工具参数**里取载荷，正文里手写的同形 JSON **不当作载荷**。

- **为什么**：这些载荷要被核心拿去驱动下一步（建 agent 会话、派发、推进或定向返工）。正文 JSON
  既没有 schema 校验、也不进工具台账，写坏就整轮失败；工具调用把"形状对不对"交给机制。
- **普通说话仍可以是正文**：不驱动核心的发言（讨论里的意见、执行席的收尾话）不必包成工具——
  这两者就是"说话"与"操作"的分界。
- **工具与载荷形状**在 `systools/tools.yaml`：`plan`（方案 + 任务链）、`node_verdict`（逐节点结论）、`checklist`（总验收清单）、`slate` / `suggest`（名单）、`submit_report`（执行席回报）。
- **载荷不合法 → 如实失败并中止这一步**（不猜、不回落正文 JSON）。

## 四、提示词按角色分配

```
prompts/
  shared/    协议、信封约定、工具协议、文案兜底、refs
  roles/     discussant / executor / planner / orchestrator
```

- **角色声明 = 提示词 + 工具面 + 渲染规则，三者同处声明**。因为**信封模式**下，该角色能用的信封清单**要渲染进该回合的上下文**（原生通道则由声明槽给出）——提示词与工具面分开声明必然漂。
- **角色必须可派生**：提示词与工具面决定了上下文与转录，重启/回档后必须重建出**同样的角色与上下文**（回放与实时产出同样的消息，是既有硬要求）。所以角色**不能**是运行时内存里的临时状态。
- **planner 与 orchestrator 分开**（上下文不同、工具面不同、指令互斥），只共享**背景知识**（链的语义、节点状态定义、信封协议）——共享的是背景，不是指令。
- **executor 是全新上下文**：讨论内容只经任务提示词带入，不继承讨论转录。

### 角色与工具面（当前）

| 角色 | 何时 | 工具面（`systools/roles.yaml`） |
| --- | --- | --- |
| `discussant` | 讨论阶段 | `say` `agree` `leave` `ask` `read` `list` `search` |
| `executor` | 任务链节点（agent 子会话） | `read` `list` `write` `edit` `patch` `search` `submit_report` + 该 agent 的模块工具 |
| `planner` | 核心整理派发 | `read` `search` `plan` `slate` `suggest` |
| `orchestrator` | 核心链中推进 | `read` `search` `node_verdict` `checklist` |

**验收不是独立角色**：它是 `orchestrator` 的一个工具/一步（"根据验收情况推进任务"本就是同一个循环）。

## 五、协作动词工具化

`say` / `agree` / `leave` / `ask` 是**声明式工具**（声明在 `systools/tools.yaml`，由角色面发放）：原生模式走供应商的结构化槽位，信封模式走**同一份声明**
渲染出的信封——两套产出同样语义，参数经同一处 schema 校验。不再是"从正文里解析自造格式"：
写坏的信封**不降级成普通发言**，而是如实记一条失败的工具行；没有信封的纯正文 = 这一轮**没表态**。

## 六、边界

| 场景 | 约定 |
| --- | --- |
| `create_session` | **当前不做**（以后的功能）：本表先不留它的席位 |
| 改任务目标 | 等于**改任务提示词**；改完**不作废**，让它跑完再由核心验收；链有问题则与用户在**主会话**讨论改链 |
| 回档 | **级联删除**子会话 |
| 系统工具调用 | 与模块工具同路径：工具行 + `[工具结果]`，可审计、可回放 |

## 七、分期与验收

| 期 | 内容 | 可判定的验收 |
| --- | --- | --- |
| **P0** | prompts 按角色归类（`builtin_tools` 段暂留原处） | 加载器从新布局装配出**同一个** `Prompts`；现有测试全绿 |
| **P1** | 转录增量外送 + 增量落盘（按一次模型调用） | 生成过程中界面逐条累积；中途刷新页面已产生部分仍在 |
| **P2** | 工具总表 + 角色表**一次做完**：声明从 prompts 搬进总表，代码读表 + 越权校验 + 悬空引用门禁 | 悬空引用让结构审查硬失败；越权调用被如实拒绝并落工具行；现有行为不变 |
| **P3** | 角色生效 + 协作动词工具化 + 讨论"同意粘住" | 原生与信封两套产出同样语义；已同意者不再被追问；重启后重建出同样状态 |
| **P4/P5** | 核心 AI 角色（planner/orchestrator）+ 审查关卡 + 任务链 | ✅ 方案与任务链由 `plan` 承载、逐节点验收 `node_verdict`、总验收 `checklist`（链的执行见 [task-chain.md](task-chain.md)） |
| **P5c** | **角色表成为机制**（不再只是提示词）：工具面与越权校验都出自它 | 讨论回合调 `write`/`edit`/`patch` 或任何模块工具 → **如实拒绝**（有测试）；单 agent 执行回合同样按 `executor` 校验；代码里没有任何"哪个角色能调哪个工具"的名单 |
| **核心操作工具化** | 五个核心操作与执行席回报都改走工具调用（见 §三之二） | ✅ 六处都从**工具参数**取载荷；正文里手写的同形 JSON 不当作载荷（有测试）；提示词只提工具调用 |
| **工具面按回合注入** | 总表不进提示词：每回合按身份注入那一份（§二），原生声明槽同一判据 | ✅ 系统提示里没有工具清单、没拿到的工具不进提示词块与声明槽（各有测试）；模块工具只在执行回合出现（`module_tools`） |
