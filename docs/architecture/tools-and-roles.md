# 工具与角色

> 本文是**系统工具、角色（身份）、以及"谁能用哪些工具"的唯一权威**。
> 模块工具仍在各自 `module.yaml` 声明（见 [MODULE_SPEC.md](../../MODULE_SPEC.md)），本文只管系统工具。

**当前状态：实施中。** 表结构与消费代码尚未落地；落地前本文描述的是**已批准的契约**，不是当前能力。

## 一、两个真相源，各一张表

| 表 | 回答什么 | 位置 |
| --- | --- | --- |
| **工具总表** | 工具**是什么**：id / desc / 参数 schema / 能否并发 / 能力 / 实现来源 | `systools/tools.yaml` |
| **角色表** | 这个**身份有什么**：引用的系统工具 id + 提示词 | `systools/roles.yaml` |

代码里**不得**出现"哪个角色能调哪个工具"的判断：只有两个动作——**按角色组装工具面**、**按表校验调用**。

### 工具表字段

```yaml
tools:
  - id: read
    desc: 读取文本文件（UTF-8）。
    params: { ... JSON Schema ... }   # 既用于生成声明，也用于校验调用参数
    parallel: true                    # 同一回复里的多个调用能否真的并发跑
    capability: fs-read               # 能力：决定收口（沙箱 / 围栏）
    impl: builtin                     # 实现来源：builtin = 核心能力
```

- **`capability` 决定收口，不按"系统/模块"一刀切**：`read`/`list`/`search`/`write`/`edit`/`patch` 虽然都是系统工具，但它们碰文件系统，**照样受沙箱与围栏约束**；`say`/`agree` 这类不碰文件。
- **列目录是"核实"的前提**：`read` 只读文件，`search` 要关键词，**没有 `list` 就确认不了"资料齐不齐、脚本在不在"**；`read` 遇到目录会如实引导到 `list`，不抛 IO 错。
- 参数不合法 → **如实拒绝并落工具行**，不静默。

### 角色表字段

```yaml
roles:
  - id: discussant
    prompt: roles/discussant          # 提示词与工具面**同处声明**
    tools: [say, agree, leave, ask, read, list, search]   # 讨论回合只做核实：读类 + 讨论动词
```

- **角色 = 场景绑定的身份**：`discussant` 只存在于讨论阶段，`orchestrator` 只存在于任务链推进阶段。**不再引入"阶段 → 工具"的第二张表**（否则两个真相源）。
- **角色表只引用系统工具**：模块工具是"这个 agent 的能力"，不是"这个角色的属性"，按成员归属自动获得。
- **不做角色继承**：重复列几个 id 没有代价，继承会引入隐式耦合。

## 二、可用工具面（运行时合成）

```
本会话可用工具 = 系统工具表 ∩ 该角色表  +  该成员所属模块的工具
```

越权防线因此分两段，缺一不可：系统工具查**角色表**；模块工具查**该成员有没有这个模块**（现状已有 module 消歧）。

## 三、越权校验

**已落地（P5c）**：角色表不再只是渲染进提示词的清单——**工具面与越权校验都出自它**：
讨论回合按 `discussant` 发放并校验（面里没有的一律拒绝），单 agent 执行回合按 `executor` 校验。
代码里**没有任何**"哪个角色能调哪个工具"的名单，加一个工具只改 `systools/tools.yaml` 与 `roles.yaml`。


- **原生模式（供应商结构化槽位）与信封模式（正文里手写信封）走同一个校验点。** 两者在项目里是**互斥但等价**的；等价性一破，回放就与实时不一致。
- 越权调用 → **如实拒绝 + 落工具行**（用户要能看到"它越权了"，而不是"AI 没反应"）。
- **悬空引用**（角色引用了总表里不存在的工具 id）→ **结构审查硬失败**。这是两张表不漂的机制保证，不靠人看。

## 四、提示词按角色分配

```
prompts/
  shared/    协议、信封约定、工具协议、文案兜底、refs
  roles/     discussant / executor / planner / orchestrator
```

- **角色声明 = 提示词 + 工具面 + 渲染规则，三者同处声明**。因为**信封模式**下，该角色能用的信封清单**要渲染进提示词**——提示词与工具面分开声明必然漂。
- **角色必须可派生**：提示词与工具面决定了上下文与转录，重启/回档后必须重建出**同样的角色与上下文**（回放与实时产出同样的消息，是既有硬要求）。所以角色**不能**是运行时内存里的临时状态。
- **planner 与 orchestrator 分开**（上下文不同、工具面不同、指令互斥），只共享**背景知识**（链的语义、节点状态定义、信封协议）——共享的是背景，不是指令。
- **executor 是全新上下文**：讨论内容只经任务提示词带入，不继承讨论转录。

### 已定的角色与工具面（P2/P3 落地）

| 角色 | 何时 | 工具面 |
| --- | --- | --- |
| `discussant` | 讨论阶段 | `say` `agree` `leave` `ask` + 文件域 |
| `executor` | 任务链节点（子会话） | 文件域 + 该 agent 的模块工具 + `submit_acceptance` |
| `planner` | 核心整理派发 | 读类 + 建链/指派（写） |
| `orchestrator` | 核心链中推进 | 读类 + 验收/暂停 |

**验收不是独立角色**：它是 `orchestrator` 的一个工具/一步（"根据验收情况推进任务"本就是同一个循环）。

## 五、协作动词工具化

`say` / `agree` / `leave` / `ask` 现在靠**从正文里解析手写信封**，格式一漂就降级成普通发言、状态会歪。改为**声明式工具**：原生模式走供应商的结构化槽位，信封模式走同一份声明渲染出的信封——**两套产出同样语义**。

## 六、边界

| 场景 | 约定 |
| --- | --- |
| `create_session` | **当前不做**（以后的功能）：本表先不留它的席位 |
| 改任务目标 | 等于**改任务提示词**；改完**不作废**，让它跑完再由核心验收；链有问题则与用户在**主会话**讨论改链 |
| 回档 | **级联删除**子会话 |
| 系统工具调用 | 与模块工具同路径：工具行 + `[工具结果]`，可审计、可回放 |

## 七、分期与验收

| 期 | 内容 | 可判定的验收 |
| --- | --- | --- |
| **P0** | prompts 按角色归类（`builtin_tools` 段暂留原处） | 加载器从新布局装配出**同一个** `Prompts`；现有测试全绿 |
| **P1** | 转录增量外送 + 增量落盘（按一次模型调用） | 生成过程中界面逐条累积；中途刷新页面已产生部分仍在 |
| **P2** | 工具总表 + 角色表**一次做完**：声明从 prompts 搬进总表，代码读表 + 越权校验 + 悬空引用门禁 | 悬空引用让结构审查硬失败；越权调用被如实拒绝并落工具行；现有行为不变 |
| **P3** | 角色生效 + 协作动词工具化 + 讨论"同意粘住" | 原生与信封两套产出同样语义；已同意者不再被追问；重启后重建出同样状态 |
| **P4/P5** | 核心 AI 角色（planner/orchestrator）+ 审查关卡 + 任务链 → **之后重新立项** | — |
| **P5c** | **角色表成为机制**（不再只是提示词）：工具面与越权校验都出自它 | 讨论回合调 `write`/`edit`/`patch` 或任何模块工具 → **如实拒绝**（有测试）；单 agent 执行回合同样按 `executor` 校验；代码里没有任何"哪个角色能调哪个工具"的名单 |
