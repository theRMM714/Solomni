# 会话模型与上下文压缩

> 本文是**"一次工作里有哪些会话、它们怎么对话、怎么同步、上下文怎么压"的唯一权威**。
> 任务链（依赖图、审查关卡、验收）见 [task-chain.md](task-chain.md)；工具与角色见 [tools-and-roles.md](tools-and-roles.md)。

**当前状态：已落地。** **执行席按 agent 一会话**（含同 agent 串行）、**讨论回合开工具循环**
（能只读核实、拿不到模块工具）、**讨论由核心驱动**（泵只决定"该问谁"，成员回合在它自己的会话里跑，
核实行与回合标记都落进那个会话；主会话只留"谁说了什么"）。
**agent 会话按需建**（第一个回合时建；等价于"讨论开始时建"）——名单确认时预建留待需要时再说。
主会话投影行带 `turn`（P5d，回档按回合同步截断）；角色表机制化（P5c）；压缩：`compact` 工具 + `compacted` 事件 + 发送视图（P6a），按模型窗口百分比自动触发（P6b）。

## 一、形态

一次工作（work）有两类会话：

```text
主会话（议场）      核心的地盘：汇总发言、出方案、挂任务链、验收、交付。
                   它自己不跑成员的工具循环。
每个在组 agent 一个会话   该 agent 在这场工作里的**完整经历**：
                   讨论时核实了什么、答应了什么、自己那些节点怎么做的、用户中途插过什么话。
```

- agent 会话**在名单确认、讨论开始时就建**（不是等节点就绪才建），命名 `<工作>--<agent>`。
- agent 会话是**普通会话**：独立上下文、独立转录、独立围栏，复用全部既有机制；**不新增会话类型**。
- **讨论与执行不分家**：同一个 agent 会话先用于讨论、后用于它的节点，上下文连贯。
- 侧栏**可见**：agent 会话挂在主会话下（`meta.parent`），用户可进入查看与发言干预。
- 侧栏顺序是**树序**，由核心给出（父会话紧跟它的子会话，深度优先、各自按时间倒序）：
  顺序与缩进是同一件事的两面，各排各的就会出现"子会话排在父会话上面"的错位。
  父会话已被删的子会话如实列在最后，不凭空消失。

## 二、回合（轮）

> **一轮 = 所有"还能发言的人"各发言过一次。**

- "还能发言" = 在组 **且** 未同意 **且** 未离开。已同意/已离开的人本轮不问（同意是粘住的）。
- 一次"发言回合"= 核心把讨论上下文交给该 agent 的会话，然后**等**；它可以在自己的会话里调工具（核实）、
  继续想，**直到用讨论动词表态**。
- **转录永远是核心的活**：子会话从不往主会话写；核心拿到动词才转录主会话并往下走。

### 计数与提醒（讨论阶段）

**模型调用次数没有上限**：子会话继续核实就继续跑，直到模型不再发起调用、或用户点「停止」。
（此前有"一轮 30 次调用"的天花板，那是在没有中止出口时用来兜底的；现在中止出口自己站住了，
天花板撤掉——它逼出来的"到顶直接收尾"正是执行席干到一半被掐断的原因。）

留下的只有**提醒次数**：这一轮对它提醒过几次（默认 3，可设置）。

- **什么时候提醒**：这一回合结束在**纯正文**（没有用讨论动词表态）时，核心**只注入一条提醒**
  （"你还没用讨论动词表态"，见下"系统消息"）——**不强制**它表态。
- 提醒次数**到顶**：本轮放它过去——主会话如实记一行 **"未回应"**，整轮继续（**不阻塞**）。
- **何时归零**：每轮开始、进入下一阶段，或它给出了讨论动词/回报时。
- **用户主动中止**时不提醒（用户可能正想和它讨论）。用户和它聊完、点「继续」后，
  它**仍要给出讨论动词**才算发过言。
- 收敛、上限、退出、请教（ask）的判定与 task-chain 一致，只是"问谁"变成"问它的会话"。

### 系统消息

系统注入的东西（提醒、压缩边界、工具围栏降级这类**不是用户说的、也不是模型说的**内容）必须有
**系统消息**这一种转录行，不能在转录与前端里长得像"用户发的"。

- 结构化信号随行落档（`system: true`），呈现层据此换样式，**不靠匹配文本**；
- 进上下文时按它该有的角色进去（提醒是给模型的指令），但**用户看到的是系统行**。

**派发行**是系统行里的一种（`system: true` + `task: true`）：核心给某个 agent 派的活。

- 界面上它和别的系统行一样是核心说的话——**不得显示成"用户"**；
- 上下文里它以 **user 角色**转发：派活是一次**回合**，而会话协议要求请求里至少有一条 user 消息，
  一条 user 都没有的请求会被供应商**整条拒收**（真机实测：全 system 的请求 400）。
  讨论席同理——它每次都用一条 user 回合（opener / step）开场。
- 两处口径都随行落档，所以**重建/回放产出发出去的那同一条消息**（见 [四之二](#四之二节点执行只有一条管道)）。

### 会话种类 × 推 / 落

**推是一处、无条件的**（底层收发该做的事）；**留不留由会话种类定**（不由调用点定）：

| 会话种类 | 推 | 落（判定只有一处：`persist_policy_for`） |
| --- | --- | --- |
| 单 agent 会话 | 定稿行 + 短暂事件 | **留**：逐轮的正文/工具/思维链——那是模型上下文的一部分，不留则重启后上下文歪 |
| 协作会话（含**核心自己的操作**） | 同上 | **留**：协议行 + 发言投影 + 核心的工具行/思维链/正文 + 派发/完成/阶段/返工通知——它是派生状态的来源，用户也要对账 |
| **系统会话**（sid 以 `#` 开头） | 同上 | **不留**：一次性动作（让核心推荐 agent、探针、一次性判定），重启后本来就该是空的；它**不进会话表**（`/api/state` 里没有它），所以前端不会为它建标签页 |

短暂事件（`Delta` 增量 / `Working` 运行态 / `ToolCall` 实时工具卡 / `Decision` 裁决卡）**任何会话都不落**——
它们只给在场的前端看；`/api/state` 与推来的事件已经把"当前该显示什么"说清。

**会话表由后端给，前端不自己造会话**：前端只为 `/api/state` 会话表里"后端说在跑"的会话建标签页，
事件流里出现**不认识的 sid** 一律不动（只置位，等下一次状态刷新把会话表带进来）。
理由：为事件里冒出来的 sid 就地建会话＝前端自己造会话状态；系统会话不是真会话，
它会因此冒出一个多余的标签页，而真会话的记录又会被建重一遍。
于是系统会话推出来的行**没有任何前端动作**：它不在会话表里、也不落盘，就是底层那一次无条件的推。

**历史与实时合流，前端不合并两个来源**：`GET /api/history/{sid}` 一次给全盘上转录 + 事件台上它之外的尾巴，
并给出合流时的头部序号当**水位**；此后 `seq ≤ 水位` 的批次丢掉、之上的按序 append（见 [contracts.md](contracts.md)）。
判据是结构化相等而不是行 id——行 id 只覆盖 `transcript` 行，`notice`/`node_started`/`report` 这些行没有 id。

**行身份是结构化字段**：一行带 `speaker`（谁说的）/ `verb`（动词：say / agree / 需求 / 开始…）/
`kind`（`msg` 模型发言 / `user` 用户说的 / `system` 系统注入或核心自己的行 / `tool` 工具行 /
`round` 轮次分隔行），**正文里不带 `[谁:动词]` 标签**。`LineView::render()` 是"字段 → 文本"的**唯一**拼法：
提示词里的转录（`{{transcript}}`）与回放比较都读它；呈现层按 `kind` 换样式、按 `speaker`/`verb` 显示身份，
不解析文本（见 [contracts.md](contracts.md) 的推的事实）。

## 二之二、谁驱动谁（实现形态，P5b-3）

> 契约要定死这一点，否则会出现两套"谁驱动谁"的说法。

**讨论不由泵自己调模型，而是"泵只决定、核心驱动"**——与任务链的节点派发**同一套路**。

理由是会话归属：生成期间协作会话被**移出核心表**（own-and-return），它碰不到表里的 agent 会话；
而 agent 会话必须留在表里，用户才能随时进去发言。所以**驱动权归核心**（它同时看得到两边）。

### 看不见的回合：运行态与逐片外送

成员回合跑在**它自己的会话**里，主会话在整回合里一个事件都收不到。所以核心要主动交代两件事，
否则用户看到的界面就是"整回合不动、只有手动刷新才同步"（真机反馈）：

- **逐片外送**：成员回合的正文逐片推 `Delta`（沿用"到 `{` 就截住"的分片规则——信封绝不当正文流出），
  核实行实时推 `ToolCall`。外送目标是**该 agent 自己的会话**（打开它的标签页就能看到它逐字在说、在读文件）。
- **逐轮定稿**：成员回合与单 agent / 节点回合跑的是**同一条轮循环**（`engine::converse_with`；
  这一回合的参数收在 `session::TurnRun`：身份、本回合工具面、本回合提示、表态约定、回合号）。
  一轮跑完就出这一轮的行（`session::build_round_lines` 是**唯一的行构造点**），
  那批行**同时入它自己的事件台与落盘**——只落盘的话，那个标签页的流式块永远等不到替换它的那一行，
  正文一直挂着闪烁光标、看着像"还在流式"。思维链随该轮的权威行保存（工具轮没有正文时挂到工具行上），
  流式结束或重放后仍可查看；没有定稿的停止/错误分片在空闲事件到达时撤下，不冒充转录。
  主会话那份是**投影**（`feed_with` 只投影"谁说了什么"），与子会话各一份、互不重复。
- **运行态的唯一真相是事件**：`SessionEvent::Working { agent }`（短暂、不落盘，`None` = 空闲）
  在"要问谁 / 这条会话开始生成"时推带名字的那条、收尾推空闲；**主会话与子会话各推各的**——
  子会话若只靠"有增量=在跑"推断，收尾就永远清不掉：那个标签页一直显示"正在工作"、按钮一直停在「停止」。
- **`/api/state` 的 `running` 是对账副本**：前端只在"本页对这条会话还没有实时知识"时用它
  （刚刷新页面、事件台裁掉一段后的重连、别人建的会话）；收到过 `Working` 之后只认事件——
  一次迟到的轮询不会把已经收尾的回合标回"在跑"；事件台出现补不齐的缺口时实时知识作废、退回对账。
  前端的按钮切换（发送/继续 ↔ 停止）、占位动画（"正在工作：某某"）都读这条运行态；
  此外"本页发出的命令还在途"也算忙——那是本地事实（防重复提交），与服务端运行态不是一回事。

### 请用户裁决：推的事件 + 快照字段

核心请用户定的事（名单确认 / 开始讨论 / 请教 / 方案待审 / 节点没过）**只有一处派生**
（`Pending::decision_parts`），推与快照是同一份事实的两面：

- **推**：`SessionEvent::Decision { kind, summary, advice, question, payload }`（短暂、不落盘）——
  界面立刻出卡，卡片是"核心的说明 + 建议 + 要你回答的那句 + **自由文本**"。
- **快照**：`/api/state` 的会话视图带 `pending`（同一形态）——刷新页面照样画得出那张卡。
- 卡片上的**建议由核心 AI 写**（随产生这一关的 `plan` / `node_verdict` 调用一起产出，不另花调用）；
  用户回应走一条命令（`decide`，自由文本）：**请教**的话进**主会话转录**（所有成员下一回合都看得到，
  不单独转给发问的成员）；**方案待审 / 节点没过**由**核心 AI 判定意图是否明确**——
  明确才开工 / 放行，模糊就不开（他的话进主会话当反馈，关卡继续等着，核心不自动往下推）。
- **改需求不是裁决**：它是会话级动作（会话视图的能力位 `can_update_task`），用户自己点；
  没有"本次需求"的会话**根本不渲染**这个按钮，会话工作中不可点。

### 泵的状态机

泵不再自己循环，而是可暂停、可恢复：

```text
泵的每一步只做三件事之一：
  AskMember { agent, msgs }   该问谁、给它什么上下文（本回合的讨论上下文）
  Notice/事件                  如实外送（轮次边界、越权、沉默…）
  Done / AskUser / Interrupted 终态
```

### 一步的完整序列

```text
1. 核心：take_collab(sid)                   协作会话移出表（own-and-return，不破不变量）
2. 核心：泵推一步 → AskMember { agent, msgs }
3. 核心：put_collab(sid)                    先放回，腾出手
4. 核心：take_single(<工作>--<agent>)       该 agent 的会话移出表
5. 核心：跑这一回合（TurnRun：动词 + 只读工具面）  与单 agent 同一条轮循环，见"逐轮定稿"
6. 核心：put_single(...)                    放回（转录增量落盘在它自己目录里）
7. 核心：投影 → 主会话追加"该 agent 的发言行"（带 turn 标记）
8. 核心：回到 1，直到泵给终态
```

- **回合标记**：第 5 步在该 agent 的会话里写一行 `[回合 tN｜第 M 轮]`（**系统行 + 系统消息**：
  不是谁说的，回档按同一口径还原）；第 7 步投影出来的主会话行带 `turn: tN`——
  两边同一个 id（回档同步靠它，见五）。
- **核实行**（只读工具的调用）落在**该 agent 的会话**里：与单 agent 的工具行同一形态，
  由同一条轮循环逐轮产出。
- **用户进 agent 会话说的话**：下一回合它自己就带着（就是同一个会话），不需要额外同步。

### 不变量

- 任何时刻**只有一个**持有者：要么核心表里、要么在跑的那一步手里（与 own-and-return 一致）；
- 主会话状态的改写**只有核心**做（泵只产出"该说什么"）；
- 一轮的边界不变：**所有"还能发言的人"各发言过一次**（见二）。

## 三、发言投影与标记

成员的**发言发生在它自己的会话里**（它调用讨论动词），由**核心投影到主会话**——主会话状态的改写只有核心做。

两边用**同一个回合 id** 对上：

| 落在哪 | 记什么 |
| --- | --- |
| agent 会话 | 该回合开头一行标记：`[回合 t17｜第 2 轮]`；其后是这一回合的工具调用与最终发言 |
| 主会话 | 投影出来的发言行带 `turn: t17` |

于是"这条发言对应它在自己会话里做的那些事"是**可跳转的事实**，回档也有确定算法（见五）。

## 四、工具面按回合给

同一个 agent 会话，**按回合**给不同的工具面：

| 回合 | 工具面 | 为什么 |
| --- | --- | --- |
| 讨论回合 | `read` / `search` / `list` + 讨论动词（say/agree/leave/ask） | 讨论只做**核实**（资料齐不齐、脚本在不在、README 怎么说）与分工；**不产出成品** |
| 执行回合 | 全工具面（文件域 + 该 agent 模块的外部工具） | 干活发生在执行回合，产物可追溯到节点、可验收 |

- **模块工具只在执行回合给**：讨论回合拿不到"干活"的手段——不是"被拒绝"，是**没有**。
- **这一份工具面是随回合注入的**：核心查"这一回合的身份能用的工具"，把那一份（说明 + 参数）作为一条
  系统消息放进该回合的上下文（原生通道同时用它做工具声明）。**整本工具总表不进提示词**——列了必然被拒
  的工具等于请模型去撞墙（细则见 [tools-and-roles.md](tools-and-roles.md) 二）。
- 角色表（`systools/roles.yaml`）声明的工具面**由机制执行**：发放（提示词块与原生声明槽）与越权校验
  同出一份表，代码里不另写名单（见分期 P5c）。

### 四之二、会话参数与对话分开

一个 agent 会话里有两类东西，**不放同一个地方**：

| | 是什么 | 放哪 | 何时进请求 |
| --- | --- | --- | --- |
| **会话参数** | 身份（agent 名 + 模块能力包）、工作环境（真实根目录）、调用约定 | `SessionParams`（结构化字段） | **每次调用现渲染**成一条系统消息 |
| **对话** | 用户说了什么、模型答了什么、调了什么工具 | `dialogue: Vec<Msg>` | 原样带上 |

请求由**唯一一处**装配（`engine::assemble`）：`[身份][本回合工具面][对话…][本回合提示]`。为什么这样分：

- 参数是**派生**的（登记处 + 提示词册 + 工作区路径）。把它渲染成"第 0 条消息"存进会话，就等于让参数冒充对话——
  回档要单独照顾那一条、压缩要给它留偏移、改一个参数（例如登记处里的工具形态）还得把整个会话从盘上重建；
- 分开之后：`rewind(0)` 就是**对话清空**；压缩只算对话的字符数；改形态只改参数里的一格，下一回合自然生效；
- **"回放与实时产出同样的消息"只约束对话本身**——对话是事实，参数是派生。

## 四之二、节点执行只有一条管道

一个节点的执行回合是**核心的能力**，不是前端的能力：核心把任务提示词作为**派发行**注入该 agent 的会话
（`note_task` / `dispatch_task`：界面上是系统行，上下文里是 **user 角色**，见上"系统消息"），
再由生成线程跑该会话；CLI 与 Web 只是各自"点火"（`drive_node` / `prepare_node`），**不各写一套派发**——
同一件事两处实现，必然一处对一处错（真实发生过两次：Web 走 `say` 把核心的任务提示词当成用户发言；
反过来把派发整条写成 system 角色，请求里一条 user 都没有，被供应商整条拒收）。

派发的生成**跟随设置里的流式开关**：节点在界面上同样逐字出（`llm_opts(true)`）。

## 五、回档：按回合标记同步

`rewind(主会话, 保留到第 L 行)` →

1. 取 L 那一行所属的 `turn`（T）；
2. 对每个 agent 会话，**截到最后一个 `turn ≤ T` 的标记行**。

两边的"这一刻"严格对上，不是各猜各的。主会话之外的痕迹（用户直接进 agent 会话说的话）随之一起被截断——
它们属于那些回合。

## 六、上下文压缩

> **压缩改的是"发给模型什么"，不是"留下什么"。转录永远完整，旧内容用户照样能查看。**

### 谁压

**AI 自己压**：核心把该会话的上下文发给 AI，只给一个工具 `compact`，提示它写下 summary。
系统**不替它总结**。

### 怎么落档

- 新增事件 `compacted { up_to: 行号, summary: "…" }` 进**转录**；
- 发送视图变成 `[system] + [摘要] + 摘要之后的行`；`up_to` 之前的内容**不再发给 AI**；
- 重启/回档按 `compacted` 事件重建发送视图；
- 界面显示**压缩分界**（"已压缩到第 N 行"）与**摘要本身**；旧内容留在上方可查（默认折叠、可展开）。

### 多次压缩 = 滚动摘要

第二次压缩的输入是"**上一份摘要 + 之后的新内容**"，输出**一份**新摘要。
无论压多少次，发送视图里永远只有一份摘要。

### 触发

| 方式 | 说明 |
| --- | --- |
| 自动 | 每次模型调用后看该次请求的 prompt tokens（优先供应商回的 `usage`；拿不到按字符估算，**界面标注"估算"**）；超过 `模型窗口 × 阈值%` → 下次调用前压一次 |
| 手动 | 输入框 `/compact` 立即压一次 |
| **不可自助** | AI **不能**在普通回合自己调 `compact`：压缩只由**系统阈值**或**用户**发起（行为可预测） |

### 设置

- `models.yaml`：每个模型声明 `context`（窗口大小，缺省保守 32k）；用户可覆盖；
- `settings.yaml`：`compact_at_percent`（默认 70）。

### 压不动就如实说

AI 没给出摘要（没调工具 / 调用失败）→ 记一条通知（"压缩没成功：…"）并**继续用完整上下文**；
用户看得到、能再试。**不静默降级、不假装压过**。

### 通用性

压缩是**所有会话通用**的能力，**单 agent 会话同样适用**。

## 七、边界语义

| 情形 | 语义 |
| --- | --- |
| 同一个 agent 的多个节点 | **串行**（一个会话一次只能跑一轮）；调度器 `ready()` 因此要加一条资源约束："该 agent 的会话空闲" |
| 不同 agent 的节点 | 照旧可并发 |
| 删主会话 | 级联：先停并删它的所有 agent 会话 |
| 删 agent 会话 | 相关节点标 Failed 并通知用户（链不静默跳过） |
| 停止主会话 | 不启新节点；已在跑的 agent 会话各自停 |
| 用户进 agent 会话发言 | 正常单 agent 一轮；它下一次发言会带上这段（讨论里能影响它），此后仍要用讨论动词表态 |
| 用户主动中止 | 计数**不再工作**（不注入提醒）；用户可能正想和它讨论 |
| 生成中的控制按钮 | 「继续」在核心调用 / 模型输出阶段**变成「中止」**——用户要能随时停，而不是只能等 |

**验收标准**

- 讨论回合调 `write`/`edit`/`patch` 或任何模块工具 → **被如实拒绝**（有测试）；
- 讨论回合能列共享区、能读模块 README（有测试）；
- 真机演示：讨论阶段**零落盘**（产物只在执行回合出现），且讨论能确认"资料齐全"；

- 压缩两次后发送视图里**只有一份摘要**，且转录完整可查（有测试）；
- 压缩失败时如实通知、继续用完整上下文（有测试）。
